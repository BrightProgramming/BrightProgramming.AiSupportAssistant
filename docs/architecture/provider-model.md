# Provider Model

The AI Support Assistant uses interfaces, factories and dependency injection to separate the application workflow from concrete implementations.

This allows knowledge sources and AI implementations to be replaced or extended without changing the core support workflow.

The application currently has three provider abstractions:

- Knowledge providers
- AI knowledge-matcher providers
- AI answer providers

Each provider type has its own interface and factory.

## The principle

The application depends on abstractions rather than directly depending on concrete infrastructure.

This means the application does not need to know whether:

- Knowledge comes from Markdown files, a database or another source.
- Knowledge matching is performed by OpenAI or another AI service.
- The final answer is generated by OpenAI or another AI service.

Factories are responsible for selecting the configured provider implementation, while dependency injection is responsible for registering and supplying the required implementations.

This keeps provider selection separate from the application workflow.

## Knowledge providers

Knowledge retrieval is defined by `IKnowledgeProvider`.

The current implementation is `MarkdownKnowledgeProvider`.

The provider is responsible for supplying knowledge to the application, while the underlying storage access is delegated to `IKnowledgeRepository`.

The current implementation follows:

**IKnowledgeProviderFactory → IKnowledgeProvider → MarkdownKnowledgeProvider → IKnowledgeRepository → MarkdownKnowledgeRepository**

The repository is responsible for accessing the underlying Markdown storage.

This keeps the knowledge provider independent from the details of how the knowledge is stored.

A different knowledge provider can be introduced without changing the Support Service or the knowledge processing workflow.

For example, future implementations could provide knowledge from:

- A database
- An API
- SharePoint
- A document store
- Another internal knowledge system

## AI knowledge-matcher providers

Knowledge retrieval and knowledge matching are separate responsibilities.

After the available knowledge has been retrieved, `IAiKnowledgeProcessor` uses an AI knowledge-matcher provider to identify the knowledge relevant to the user's question.

The provider abstraction is `IAiKnowledgeMatcherProvider`.

The current implementation is `OpenAiKnowledgeMatcherProvider`.

The provider is obtained through `IAiKnowledgeMatcherFactory`.

The current implementation therefore follows:

**IAiKnowledgeMatcherFactory → IAiKnowledgeMatcherProvider → OpenAiKnowledgeMatcherProvider → OpenAI**

The matcher receives the user's question together with the available knowledge and identifies the documents that are relevant.

The resulting `KnowledgeContext` contains the relevant knowledge that can then be supplied to the answer-generation stage.

This separation means that the mechanism used to determine relevance can be changed independently of the knowledge storage implementation and the final answer provider.

## AI answer providers

The final answer-generation stage is defined by `IAiAnswerProvider`.

The current implementation is `OpenAiAnswerProvider`.

The provider is obtained through `IAiAnswerProviderFactory`.

The current implementation follows:

**IAiAnswerProviderFactory → IAiAnswerProvider → OpenAiAnswerProvider → OpenAI**

`OpenAiAnswerProvider` provides the OpenAI implementation behind the `IAiAnswerProvider` abstraction.

It receives the user's question together with the relevant `KnowledgeContext` and generates the final answer.

The rest of the application does not need to depend directly on the OpenAI implementation.

Other implementations of `IAiAnswerProvider` could be introduced in the future.

For example, an organisation could provide an implementation for:

- Another hosted AI service
- A locally hosted model
- An internal AI gateway

## Provider factories

Each provider type has a corresponding factory responsible for selecting the configured implementation.

The current provider factories are:

| Factory | Provider |
|---|---|
| `IKnowledgeProviderFactory` | `IKnowledgeProvider` |
| `IAiKnowledgeMatcherFactory` | `IAiKnowledgeMatcherProvider` |
| `IAiAnswerProviderFactory` | `IAiAnswerProvider` |

The factories allow the processors to work with abstractions rather than concrete provider classes.

For example, `KnowledgeProcessor` obtains its knowledge provider through `IKnowledgeProviderFactory`.

Similarly, `AiKnowledgeProcessor` obtains its knowledge-matcher provider through `IAiKnowledgeMatcherFactory`.

`AiAnswerProcessor` obtains its answer provider through `IAiAnswerProviderFactory`.

This keeps the selection of concrete implementations separate from the application workflow.

## Dependency injection

Provider implementations are registered with the application's dependency injection container.

This allows the required factories, processors, providers and repositories to be supplied to the application without the consuming components creating those dependencies themselves.

The provider factory then selects the configured implementation used by the relevant processor.

This provides two separate responsibilities:

- **Dependency injection** supplies the available implementations.
- **Provider factories** select the implementation required by the application configuration.

## Adding your own provider

The provider model is designed so that additional implementations can be introduced without changing the core support workflow.

### Adding a knowledge provider

To add a new knowledge provider:

1. Implement `IKnowledgeProvider`.
2. Implement or reuse an appropriate `IKnowledgeRepository` if required.
3. Register the implementation with dependency injection.
4. Configure the knowledge provider selection.

The existing `KnowledgeProcessor` does not need to know how the new provider retrieves its knowledge.

### Adding an AI knowledge matcher

To add a new knowledge-matching implementation:

1. Implement `IAiKnowledgeMatcherProvider`.
2. Register the implementation with dependency injection.
3. Configure the knowledge-matcher provider selection.

The `AiKnowledgeProcessor` does not need to know how the matcher determines relevance.

### Adding an AI answer provider

To add a new answer provider:

1. Implement `IAiAnswerProvider`.
2. Register the implementation with dependency injection.
3. Configure the answer-provider selection.

The `AiAnswerProcessor` does not need to know which AI service generates the answer.

## The complete provider model

The provider architecture can be summarised as three independent provider pipelines.

### Knowledge

**KnowledgeProcessor**

↓

**IKnowledgeProviderFactory**

↓

**IKnowledgeProvider**

↓

**MarkdownKnowledgeProvider**

↓

**IKnowledgeRepository**

↓

**MarkdownKnowledgeRepository**

↓

**Markdown files**

### Knowledge matching

**AiKnowledgeProcessor**

↓

**IAiKnowledgeMatcherFactory**

↓

**IAiKnowledgeMatcherProvider**

↓

**OpenAiKnowledgeMatcherProvider**

↓

**OpenAI**

### Answer generation

**AiAnswerProcessor**

↓

**IAiAnswerProviderFactory**

↓

**IAiAnswerProvider**

↓

**OpenAiAnswerProvider**

↓

**OpenAI**

The three pipelines have deliberately separate abstractions because retrieving knowledge, identifying relevant knowledge and generating an answer are different responsibilities.

## Why use this approach?

The provider model provides:

- **Separation of concerns** — application logic is separated from infrastructure.
- **Replaceability** — implementations can be exchanged without changing the processing workflow.
- **Extensibility** — new providers can be added as the application evolves.
- **Testability** — provider interfaces can be replaced with test implementations.
- **Reduced coupling** — the application is not tied directly to a particular knowledge store or AI service.
- **Independent evolution** — knowledge retrieval, knowledge matching and answer generation can evolve independently.

## A practical example

The current implementation demonstrates the provider model using Markdown and OpenAI.

For knowledge retrieval:

**IKnowledgeProvider**

is implemented by:

**MarkdownKnowledgeProvider**

which uses:

**MarkdownKnowledgeRepository**

to access the Markdown knowledge source.

For knowledge matching:

**IAiKnowledgeMatcherProvider**

is implemented by:

**OpenAiKnowledgeMatcherProvider**

which uses OpenAI to identify relevant knowledge.

For answer generation:

**IAiAnswerProvider**

is implemented by:

**OpenAiAnswerProvider**

which uses OpenAI to generate the final answer.

The Support Service does not need to know about any of these concrete implementations.

It works with the processors, which in turn work with the appropriate abstractions.

## Summary

The provider model is a key part of the application's architecture.

Interfaces define the capabilities required by the application, while concrete providers implement those capabilities.

Factories select the configured providers, while dependency injection supplies the available implementations.

The current implementation uses:

- Markdown for knowledge storage.
- OpenAI for knowledge matching.
- OpenAI for answer generation.

The architecture provides clear extension points for alternative knowledge sources, knowledge-matching implementations and AI answer providers.

This allows the core support workflow to remain stable while the infrastructure behind it can evolve independently.
