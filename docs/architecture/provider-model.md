# Provider Model

The AI Support Assistant uses interfaces to separate the application workflow from the underlying implementations.

This allows knowledge and AI implementations to be replaced or extended without changing the core application flow.

## The principle

The Support Service depends on abstractions rather than concrete implementations.

The application therefore does not need to know whether knowledge comes from Markdown files, a database or another source, or whether responses are generated by OpenAI or another AI service.

## Knowledge providers

Knowledge retrieval is defined by `IKnowledgeProvider`.

The current implementation is `MarkdownKnowledgeProvider`.

`MarkdownKnowledgeProvider` uses `MarkdownKnowledgeRepository` to read the underlying Markdown files.

This keeps the responsibilities separate:

- `IKnowledgeProvider` defines how knowledge is retrieved.
- `MarkdownKnowledgeProvider` coordinates the knowledge retrieval process.
- `MarkdownKnowledgeRepository` handles reading the Markdown files.

A different knowledge implementation can be added without changing the Support Service.

For example, an application could provide:

- `MarkdownKnowledgeProvider`
- `DatabaseKnowledgeProvider`
- `ApiKnowledgeProvider`

All can implement the same `IKnowledgeProvider` interface.

## AI providers

AI integration follows the same principle.

The application depends on an AI provider abstraction rather than directly depending on a specific AI service.

The current implementation uses OpenAI, but another implementation can be introduced without changing the application workflow.

For example, an application could provide:

- `OpenAIProvider`
- `AzureOpenAIProvider`
- `LocalAIProvider`
- An organisation's own AI service

The exact implementation is hidden behind the provider abstraction.

## Adding your own provider

To add a new knowledge provider:

1. Implement `IKnowledgeProvider`.
2. Add any supporting classes required by the implementation.
3. Register the implementation with dependency injection.
4. Configure the application to use it.

The same approach can be used when adding or replacing an AI provider.

The important point is that the `SupportService` does not need to change.

## Why use this approach?

The provider model provides:

- **Separation of concerns** — application logic is separated from infrastructure.
- **Replaceability** — implementations can be exchanged without changing the workflow.
- **Extensibility** — new providers can be added as the application evolves.
- **Testability** — provider interfaces can be replaced with test implementations.
- **Reduced coupling** — the application is not tied to a particular knowledge store or AI service.

## Summary

The provider model is a key part of the application's architecture.

The application depends on interfaces such as `IKnowledgeProvider` rather than concrete infrastructure implementations.

This means the same application workflow can work with different knowledge sources and AI services without requiring changes to the Support Service.
