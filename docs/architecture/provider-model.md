# Provider Model

The AI Support Assistant uses interfaces and factories to separate the application workflow from concrete implementations.

This allows knowledge and AI implementations to be replaced or extended without changing the core support workflow.

## The principle

The application depends on abstractions rather than directly depending on concrete infrastructure.

This means the application does not need to know whether knowledge comes from Markdown files, a database or another source, or whether an AI response is generated by OpenAI or another AI service.

Factories are used to obtain the configured provider implementations.

## Knowledge providers

Knowledge retrieval is defined by `IKnowledgeProvider`.

The current implementation is `MarkdownKnowledgeProvider`.

The provider is responsible for supplying knowledge to the application, while the underlying storage access is delegated to a repository.

The current implementation follows:

**IKnowledgeProvider → MarkdownKnowledgeProvider → IKnowledgeRepository → MarkdownKnowledgeRepository**

This keeps the knowledge provider independent from the details of how the knowledge is stored.

A different knowledge provider can be introduced without changing the Support Service.

For example, future implementations could provide knowledge from:

- A database
- An API
- SharePoint
- A document store
- Another internal knowledge system

## AI providers

The AI side of the application uses provider abstractions for the different AI responsibilities.

The current answer implementation follows:

**IAiAnswerProvider → OpenAiAnswerProvider → OpenAI**

`OpenAiAnswerProvider` provides the OpenAI implementation behind the `IAiAnswerProvider` abstraction.

The rest of the application does not need to depend directly on the OpenAI implementation.

Other implementations of `IAiAnswerProvider` could be introduced in the future.

For example, an organisation could provide an implementation for another hosted AI service or a locally hosted model.

## Provider factories

Factories are used to obtain the configured provider implementations.

For example, the knowledge processing workflow uses `IKnowledgeProviderFactory` to obtain the configured `IKnowledgeProvider`.

This keeps the selection of a concrete implementation separate from the application workflow.

The same principle is used for the AI answer provider.

## Adding your own provider

To add a new knowledge provider:

1. Implement `IKnowledgeProvider`.
2. Add any supporting repository or processing classes required by the implementation.
3. Register the implementation with dependency injection.
4. Configure the application to use it.

To add a new AI answer provider:

1. Implement `IAiAnswerProvider`.
2. Add the implementation for the required AI service.
3. Register the implementation with dependency injection.
4. Configure the application to use it.

The core support workflow does not need to know which concrete implementation is being used.

## Why use this approach?

The provider model provides:

- **Separation of concerns** — application logic is separated from infrastructure.
- **Replaceability** — implementations can be exchanged without changing the workflow.
- **Extensibility** — new providers can be added as the application evolves.
- **Testability** — provider interfaces can be replaced with test implementations.
- **Reduced coupling** — the application is not tied directly to a particular knowledge store or AI service.

## A practical example

The current Markdown knowledge implementation demonstrates the approach.

The application works with the abstraction:

**IKnowledgeProvider**

The concrete implementation is:

**MarkdownKnowledgeProvider**

And the storage implementation is:

**MarkdownKnowledgeRepository**

The Support Service does not need to change if the Markdown implementation is replaced by another provider.

The same principle applies to the AI implementation:

**IAiAnswerProvider**

is implemented by:

**OpenAiAnswerProvider**

The application therefore has a consistent workflow while allowing the infrastructure behind that workflow to change.

## Summary

The provider model is a key part of the application's architecture.

Interfaces define the capabilities required by the application, while concrete providers implement those capabilities.

Factories and dependency injection keep the selection of implementations separate from the core workflow.

The current implementations use Markdown for knowledge storage and OpenAI for answer generation, but the architecture provides clear extension points for alternative implementations.
